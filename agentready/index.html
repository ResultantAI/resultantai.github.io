How it works

Four steps, and the last one is the product

Anyone can hand an agent a phone line now. A phone line is not an answer. The answer, and the evidence behind it, is what you are paying for.

01
Discover
Your agent reads the discovery document at /.well-known/agentready.json or llms.txt and finds verify.by_phone.
02
Ask
It sends a business, a number, and up to six questions, each with an answer type, so a price comes back as a number and not a sentence.
03
Call
AgentReady places the call, opens with an automated call disclosure, asks the questions, and retries if it reaches voicemail.
04
Answer, with receipts
Each answer comes back structured, with the verbatim transcript quote that produced it and a confidence value. Your agent polls verify.get for the result.
How an agent pays, today

Your agent starts the purchase. A human settles it.

For agent builders. A machine client that calls a paid tool gets a real HTTP 402 with a checkout rail. It posts the same request to the rail, gets back a checkout link for its human, and polls for the result. That is the live rail today.

# 1. call the paid tool POST verify.by_phone → 402 { error: "payment_required", item, rails: ["checkout"] } # 2. post the same body to the rail POST accepts.url → 200 { verification_id, checkout_url, poll_url } # 3. a human opens checkout_url and pays. the agent polls. GET poll_url → answers, quotes, confidence

Straight answers

What it is not, yet

You will ask these anyway. Better you read them here.

It is not real time
A phone call takes minutes, and a voicemail retry takes longer. There is no turnaround guarantee, because one completed call is not a service level.
It is not proven at volume
The full chain works: request, live payment, outbound call, live conversation, extraction, structured result. It has been run end to end. Pickup rate and accuracy have not been measured across a real sample yet. When they are, the numbers go on this page, whatever they are.
Self-serve batch and API keys are not live
Today it is one call per request. Prepaid credits, an API key and a batch endpoint are next, and they get built with the first teams who need them. That is what the call below is for.
No purchase happens without a human approval
Every payment today needs a person to approve it, by checkout or by one tap. Machine payments through Stripe's Machine Payments Protocol are tested end to end in Stripe's sandbox and are not live. The live rail is checkout.
Caller ID is not verified yet
Verification is submitted and pending. Until it clears, the call can show up as an unknown number.
The confidence value is a hint
It has not been calibrated against measured accuracy. The quote is the evidence. Read the quote.

What builders ask first

The questions before the integration

I could build this myself.
You could. The telephony is the easy part. The conversation design, the extraction, typed answers, the retry logic, the call disclosure and the evidence trail are the rest of it. Build it if it is your core product. Call a tool if it is not.
Is it legal to have an AI call a business?
It is a real question and it gets treated like one. Every call opens with an automated call disclosure, calls have a hard length cap, and there is a daily call cap per requester. None of that is legal advice, and if your use case has its own rules, they are yours to know.
What happens when it gets an answer wrong?
You can see it, because the quote that produced the answer comes back with it. A system that hides its source makes you trust it. This one shows you the words and lets you decide.
